# everycard 설계 문서 (초안 v1)

작성일 2026-11-25. Luchenia와의 설계 대화를 정리한 문서입니다. **[결정]** 은 Luchenia가 정한 것, **[제안]** 은 Claude가 채운 것으로 검토와 수정 대상입니다.

---

## 1. 무엇을, 왜

2D 도트 탑뷰 턴제 카드 로그라이크. 플레이어 캐릭터와 몬스터가 격자 전장에서 번갈아 카드를 쓰고, 카드는 중력, 온도, 압력, 시공간 같은 **많은 변인**을 조절한다. 변인들은 서로 맞물려 예상 밖의 연쇄를 만든다. **[결정]**

이 게임만의 차별점은 두 가지다.
1. **변인 시뮬레이션 전투**: 카드 한 장의 효과가 전장의 물리(와 약간의 판타지) 규칙을 통해 다른 카드, 지형, 적과 상호작용한다.
2. **유저가 만드는 카드**: 플레이어가 카드 이름과 그림만 만들어 올리면 LLM이 그것을 보고 효과와 밸런스를 정하고, 그 카드가 모든 플레이어에게 공유된다. 플레이가 쌓일수록 카드 풀이 커진다. **[결정]**

장르 메커니즘(덱 빌딩 로그라이크, 갈래길 맵)은 기존 장르를 참고하되, 이름, 캐릭터, 카드, 아트는 모두 오리지널이다.

### 목표
- 스팀 유료 출시가 메인. **[결정]**
- 출시 전 웹 무료판으로 홍보는 비용과 리스크가 작을 때만. **[결정]**
- 웹판은 따로 만들지 않고 같은 Godot 프로젝트를 웹으로 내보낸 **체험판**으로 한다. 스팀 기능과 카드 제작은 끄고, 공유 카드는 읽기만. 스팀 체험판(Next Fest)과 같은 빌드에서 나온다. 체험판 공개 시점은 런 구조 단계 이후. **[제안]**
- 웹 내보내기 제약: GDScript만(C# 불가), Compatibility 렌더러, 단일 스레드 내보내기로 itch.io 등에서 특수 헤더 없이 실행, 스팀 플러그인은 웹에서 동작하지 않으므로 기능 분기 필요. **[제안]**
- LLM이 "무제한급"으로 다양한 효과를 지어낼 수 있을 만큼 변인과 동작 부품이 풍부할 것. **[결정]**

### 하지 않을 것 (v1 범위 밖) [제안]
- 실시간 멀티플레이나 PvP
- 웹판에서의 카드 제작
- 모바일 출시

### 실패로 볼 것 (돌아가도 실패) [제안]
- LLM이 코드나 규칙 밖의 효과를 만들어내는 구조. LLM은 정해진 부품만 조합한다.
- 검수를 너무 빡빡하게 걸어 유저 카드의 재미와 의외성이 식는 것. **[결정]** 초반에 밸런스 붕괴 카드나 자극적인 카드가 노출될 수 있음은 감수하고, 빠른 신고와 대응으로 덮는다.
- 법적 처벌 대상 수준의 콘텐츠가 빠르게 내려가지 않는 것. **[결정]**
- 변인은 많은데 화면에서 읽히지 않아 플레이어가 왜 그런 결과가 났는지 모르는 것. 변인 수만큼 **가독성**이 중요하다.

## 2. 전투

### 2.1 전장 [결정 + 제안]
- 칸이 있는 격자 전장, 탑뷰, 게임 전체 화면. **[결정]**
- 크기 약 9×7 칸. **[제안, 프로토타입에서 조정]**
- 세 겹 구조 **[결정]** 와 전장 전체 값 한 겹 **[제안]**:
  1. 칸의 값: 온도, 압력, 중력(방향+세기), 시간 속도 등 숫자/방향
  2. 칸의 물질: 물, 얼음, 기름, 가스, 불, 벽 등. 환경값에 반응해 상태가 바뀜
  3. 유닛의 값: 체력, 질량, 저항, 상태(젖음, 감전 등)
  4. 전장 전체 값: 날씨, 낮밤, 기본 중력, 기본 시간 흐름 등
- 변인 목록 초안: [variables-v1.md](../../design/variables-v1.md) (약 100종). 변인 수는 계속 늘어날 수 있어야 한다. **[결정]**

### 2.2 변인 정의 방식 [제안]
모든 변인은 데이터로 정의한다. 하나의 변인은 범위와 기본값, 퍼짐률(턴마다 이웃 칸으로 번지는 정도), 회복률(기본값으로 돌아가는 정도), 반응 규칙, 화면 표시 방법을 가진다.

변인끼리의 상호작용은 짝마다 코드로 짜지 않고 **"조건 → 결과" 반응 규칙 표**로 정의한다.
예: `온도 >= 100 AND 물질 == 물 → 물질 = 증기, 압력 += 2`

그래서 새 변인 추가는 데이터와 규칙만 넣는 일이고, LLM은 같은 카탈로그를 부품 목록으로 받는다. 유저 카드에서 자주 요구되는데 없는 변인은 로그로 모아 운영자 승인 후 새 변인으로 승격한다.

### 2.3 해석 범위 [결정]
물리 규칙이 바탕이고, 카드 맥락에 맞게 판타지와 추상까지 그 사이를 조절한다. 구현상으로는 물리 변인 + 소수의 정식 추상 변인(감정 기운, 운, 엔트로피, 마력 밀도)으로 표현한다. LLM이 카드마다 새 상태를 만들어내지 않게 한다. **[제안]**

### 2.4 턴 구조
- 플레이어 턴: 시간 예산(예: 10)을 가지고 카드를 쓴다. 카드마다 시간 비용이 있다. **[결정: 시간 비용 방식]**
- 이동: 자기 턴에 기본 1칸 이동 가능. 더 먼 이동은 카드로. **[결정]** 기본 1칸 이동은 시간 비용 없음. **[제안]**
- 적: 전 턴에 노릴 칸을 예고하거나 즉시 공격한다. **[결정]** 예고는 칸 위에 표시하고, 적 턴 시작에 해결된다. 시공간 카드로 예고를 한 턴 밀 수 있다. **[제안]**
- 환경 단계: 각 진영의 턴이 끝날 때 시뮬레이션이 한 번 돈다(퍼짐, 반응, 중력/압력에 의한 이동). 칸의 시간 속도가 그 칸의 틱 수/배율을 바꾼다. **[제안]**
- 순서 예: 플레이어 턴 → 환경 단계 → 적 턴(예고 해결, 새 예고/즉시 공격) → 환경 단계 → 반복. **[제안]**
- 연쇄 반응은 한 환경 단계에서 상한(예: 칸당 반응 8회)을 둬 무한 루프를 막는다. **[제안]**

### 2.5 흐르는 손패 [결정]
- 손패 5칸이 컨베이어처럼 흐른다. 턴이 끝나면 1칸 흐르고, 왼쪽 끝 카드는 버림 더미로, 오른쪽 빈칸은 덱에서 채운다.
- 쓴 카드 자리는 빈칸으로 남고 턴 끝에 채워진다. 많이 쓰면 회전이 빨라진다. **[제안]**
- 다음에 들어올 카드 1장을 미리 보여준다. **[제안]**
- 속도 손잡이 세 개 **[결정]**:
  1. 붙잡기(시간을 써서 이번 턴 흐름 멈춤), 흘려보내기(공짜로 1칸 더 흘림)
  2. 내가 선 칸의 시간 속도가 벨트 속도에 곱해짐
  3. 카드 무게: 무거운 카드는 한 칸 넘어가는 데 2턴. 중력 변인이 무게에 영향. 유저 카드는 LLM이 무게도 정한다.
- 적이 벨트를 가속/동결하는 공격, 맵 보상으로 손패 칸 증가. **[제안]**
- 수치(5칸, 1칸, 시간 10)는 프로토타입에서 정한다.

### 2.6 카드 효과 표현 [제안]
카드 효과는 **부품 목록(JSON)** 이다. 부품 종류:
- 대상 지정: 자신, 칸 하나, 모양(직선, 원, 부채꼴, 십자, 전체), 유닛 선택 조건
- 칸의 값 바꾸기: 어느 변인을, 더하기/곱하기/설정, 얼마나, 몇 턴 동안
- 물질 놓기/없애기/변환
- 유닛 조작: 피해(종류별), 회복, 밀기/당기기, 순간이동, 상태 부여/제거, 고유값 변경
- 투사체/광선: 경로를 따라 이동하며 변인의 영향을 받음(중력, 반사, 굴절, 공간 곡률)
- 지연과 조건: N틱 후 발동, "만약 칸이 젖어 있으면" 같은 조건
- 메타: 손패 벨트 조작, 시간 예산 조작
- 카드 속성: 시간 비용, 무게, 희귀도

모든 부품은 **위력 점수**를 가진다. 카드 하나의 총 위력은 희귀도별 예산 안에 있어야 한다(렉시포지의 "발동 위력 예산" 방식 참고). 위력 계산기는 데이터 기반으로 만들어 게임과 서버가 같은 규칙 파일을 쓴다.

### 2.7 적 [제안]
- 적도 같은 부품 시스템으로 된 카드를 쓴다. 적마다 작은 고정 덱과 행동 패턴(약간의 무작위)을 가진다.
- 적의 카드 역시 변인을 건드려 플레이어가 그 변인을 역이용할 수 있다(적이 깔아둔 물 위로 전기).
- 초기 적: 일반 3~4종, 정예 1~2종, 보스 1종으로 시작.

### 2.7.1 의외성 부품 [결정]
유저 카드가 적의 덱에 들어가기, 적의 카드 훔치기, 적 자체를 카드화해서 소환하기 같은 덱/카드 이동도 변인의 일부다. 효과 부품에 다음을 추가한다. **[제안: 구체 부품]**
- 카드 이동: 적 덱/손패에서 훔치기, 내 카드를 적 덱에 심기, 카드 복제, 카드 변환
- 유닛 카드화: 쓰러뜨린(또는 약화된) 적을 카드로 만들어 덱에 넣고, 쓰면 아군 유닛으로 소환
- 적이 쓰는 덱에 유저 카드 풀에서 뽑은 카드가 섞일 수 있음(적 전용 위력 보정 적용)
- 이를 위해 플레이어 쪽 아군 유닛(소환수) 개념과 적의 덱/손패 상태가 시뮬레이션에 포함된다.

### 2.8 가독성 [제안]
- 칸 위 덧칠과 입자로 주요 변인 표시, 마우스를 올리면 칸의 전체 값 표시
- 카드를 들고 칸을 가리키면 **예상 결과 미리보기**(영향 받는 칸, 예상 피해, 밀림 방향)
- 연쇄 반응은 순서대로 짧게 재생하고, 전투 로그에 "증기 → 압력 상승 → 밀려남" 식으로 남김

## 3. 캐릭터 [결정 + 제안]
- 시작 덱이 다른 여러 캐릭터. **[결정]**
- 캐릭터마다 기본 능력이 다를 수 있다. 예: 기본 1칸 이동 대신 다른 능력. **[결정]**
- 출시 목표 3~4명, 프로토타입은 1명. 예시 **[제안]**: 걷는 자(기본 1칸 이동), 열 다루는 자(이동 대신 발밑 칸 온도 ±), 중력 다루는 자(이동 대신 인접 유닛 1칸 끌기), 시계공(이동 대신 손패 벨트 1칸 조작).
- 모든 캐릭터는 처음부터 선택 가능. **[제안]**

## 4. 런과 맵 [결정 + 제안]
- 판과 판 사이 영구 성장 없음. 매 판 새로 시작. **[결정]** 게임의 장기 성장은 유저 카드 풀이 커지는 것 자체다. 해금 시스템은 두지 않는다. **[제안]**
- 한 판 1~3시간. **[결정]** → 런 도중 저장하고 끄기(이어하기)가 필수. 저장은 각 방 진입 시점 기준, 전투 중 저장은 턴 시작 시점 스냅샷. **[제안]**
- 라운드가 끝나면 다음 방을 선택지로 고른다. 선택지 종류: ???방, 적대 몬스터 방, 이벤트 등. 내용은 대략적으로만 보여준다. **[결정]**
- 매 판 시드에 따라 맵 구조와 선택지가 달라진다. **[결정]**
- 구조: 3개 구역, 구역마다 약 12~15단계의 갈래길 그래프, 각 구역 끝에 보스. **[제안]**
- 방 종류 **[제안]**: 전투, 정예 전투, ???(열어보기 전까지 종류 모름), 이벤트, 상점, 휴식(회복 또는 카드 강화), 보스
- "대략적으로만": 방 종류 아이콘과 위험도 정도만 보이고, ???는 종류도 안 보임. **[제안]**
- 전투 시드도 런 시드에서 파생해 같은 시드면 같은 결과가 나오게 한다(버그 재현용). **[제안]**
- 보상: 전투 후 카드 3장 중 1장 선택. 후보는 기본 카드 풀과 유저 카드 풀을 섞는다(비율은 운영 수치). **[제안]**

## 5. 유저 카드 제작과 공유

### 5.1 흐름
1. 클리어 또는 특정 이벤트에서 카드 제작권을 얻는다. **[결정]**
2. 카드 이름 입력, 카드 그림을 직접 그린다. **[결정]** 그림은 게임 안의 도트 캔버스(예: 32×32 또는 48×48, 제한된 팔레트)로 그린다. 외부 이미지 업로드는 받지 않는다. 스타일 통일과 검수 부담 감소 때문. **[제안]**
3. 서버로 업로드 → LLM이 이름과 그림을 보고 효과를 정한다. **[결정]**
4. 효과는 업로드 시 한 번 정해지고 모든 플레이어에게 똑같이 고정된다. **[결정]**
5. 만든 사람에게 결과를 보여준다. 공개 전에 한 번 "폐기"만 가능하고 다시 뽑기는 안 된다. **[제안]**

### 5.2 서버 처리 단계 [제안]
1. **검수 (느슨하게)** **[결정: 방향]**: 자극적인 주제는 허용한다. 업로드 단계에서 막는 것은 법적 처벌 대상이 명확한 것만(아동 성적 콘텐츠, 실존 인물 대상 성적 콘텐츠/명예훼손, 개인정보, 범죄 실행 정보 등) **[제안: 목록]**. 나머지는 통과시키고 등급 태그(예: 폭력, 성적 암시, 혐오 표현 의심)를 붙여 플레이어가 설정에서 걸러 볼 수 있게 한다. **[제안]**
2. **효과 설계**: LLM이 변인 카탈로그와 부품 스키마, 희귀도 예산, 예시 카드를 받고 부품 JSON을 출력. 이름과 그림의 맥락에 맞게 물리/판타지 비율을 조절.
3. **검증**: 서버의 위력 계산기가 스키마 적합성과 예산을 검사. 초과면 한 번 재요청, 그래도 초과면 수치를 비례 축소.
4. **카드 문구 생성**: 부품 JSON에서 효과 설명문을 규칙 기반으로 생성(LLM 문구가 실제 효과와 어긋나지 않게).
5. **저장과 공개**: 카드 DB에 저장, 카드 풀에 편입.
- LLM 호출은 카드 제작 시에만 일어나므로 비용은 플레이 횟수와 무관하다.

### 5.3 평가와 운영 [결정 + 제안]
- 본인이 직접 얻어본 남의 카드에만 좋아요, 싫어요, 신고를 할 수 있다. **[결정]**
- 운영자가 문제 카드를 수정한다. **[결정]**
- 목표는 빠른 신고 대응. **[결정]** 신고 사유가 "불법"이면 1건만으로도 즉시 숨김 후 운영자 검토, 일반 신고는 누적 기준으로 숨김. **[제안]** 싫어요 비율이 높은 카드는 등장 가중치를 낮춤. **[제안]**
- 운영자 도구: 카드 목록, 신고 큐, 효과 JSON 수정, 숨김/삭제, 제작자 제재. **[제안]**
- 카드를 수정하면 버전이 올라가고 모든 플레이어에게 새 버전이 적용됨. **[제안]**

## 6. 기술 구성

### 6.1 방식 비교
| 방식 | 장점 | 단점 |
|---|---|---|
| A. Godot 4.7.2 + 관리형 서버 (Supabase 등) | 렉시포지와 같은 엔진이라 경험과 위력 예산 개념 재사용, 스팀 연동 플러그인, 웹 내보내기 가능, 서버 운영 부담 적음 | 위력 계산기가 게임(GDScript)과 서버(TypeScript) 양쪽에 필요 |
| B. TypeScript 웹 게임 + 데스크톱 포장 | 게임과 서버가 코드 공유, 웹판 쉬움 | 렉시포지 자산 재사용 불가, 도트 게임 툴을 직접 갖춰야 함 |

**[결정] A안: Godot + 관리형 서버.**

### 6.2 A안 세부 [제안]
- 게임: Godot 4.7.2, GDScript. 렌더러 Compatibility(웹 내보내기 호환).
- 시뮬레이션 코어(변인, 반응, 카드 부품 실행)는 화면과 분리된 순수 로직으로 작성해 헤드리스 테스트 가능하게.
- 데이터: 변인 카탈로그, 반응 규칙, 부품 스키마, 위력 점수표를 JSON 파일로. 게임과 서버가 같은 파일을 읽고, 공용 테스트 사례 파일로 두 계산기 결과가 같은지 검사.
- 서버: Supabase (Postgres, 그림 저장소, 서버 함수). 스팀 로그인은 스팀 인증 티켓을 서버 함수에서 검증.
- LLM: Claude API(비전 지원 모델). 구조화된 출력으로 부품 JSON을 받음. 모델은 비용과 품질을 보고 결정.
- 오프라인: 카드 풀을 로컬에 캐시. 서버 없이도 기본 카드와 캐시된 카드로 플레이 가능.
- 스팀: GodotSteam 플러그인.
